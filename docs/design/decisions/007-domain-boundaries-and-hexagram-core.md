# ADR-007：术数领域边界与公共卦象核心

> 状态：第一阶段已实现，术数映射待专家签署
> 日期：2026-08-16

## 1. 问题

早期MVP将历法、八卦常量、六十四卦查表和各体系算法集中在`app/core`。梅花和六爻曾从周易模块导入卦象派生函数，虽然函数本身只计算阴阳爻，但依赖方向会造成“公共数学事实属于周易”的错误边界，并为后续误用体用、世应、纳甲或三传规则留下风险。

本决策只完成公共卦象第一阶段，不扩展历法、纳甲、体用或三传算法。

## 2. 强制边界

后端公开领域入口为：

```text
app/
├── calendar/    中国历法公开入口
├── common/      阴阳爻、八卦、六十四卦和纯数学转换
├── zhouyi/      周易起卦规则
├── liuyao/      六爻起卦、世应、纳甲等规则
├── meihua/      梅花起卦、体用等规则
└── daliuren/    大六壬四课三传等规则
```

允许的依赖方向：

```text
calendar ──────┐
common ────────┼──> zhouyi / liuyao / meihua / daliuren
               └──> API
```

各术数体系不得导入其他体系的engine。共享内容必须先证明是无流派含义的数学或历法事实，再进入`common`或`calendar`。

明确禁止：

- 梅花体用进入六爻世应计算。
- 六爻纳甲进入梅花排盘。
- 周易动爻函数生成大六壬三传。
- 大六壬四课三传由自然语言或LLM补全。

`app/core`暂时作为兼容实现目录保留，公开API已通过各领域package导入。后续阶段每次迁移一个体系的内部文件，不在本次做无行为收益的大规模移动。

## 3. 公共数据模型

`app/common`使用冻结的dataclass：

- `Line`：只接受0阴、1阳，支持不可变阴阳转换。
- `Trigram`：编号、名称、符号、三爻、五行和方位；爻序固定为自下而上。
- `Hexagram`：文王序、名称、符号、下卦和上卦；六爻由下卦三爻加上卦三爻组成。
- `ChangeResult`：本卦、变卦、动爻位置、变化前后爻值和计算轨迹。

八卦编号采用当前工程基线`乾1、兑2、离3、震4、巽5、坎6、艮7、坤8`。六十四卦采用文王序矩阵。两者是版本化工程基线，不代表已完成流派专家签署。

## 4. 确定性与轨迹

公共函数不访问时间、数据库、随机源、网络或LLM，不修改全局状态。相同输入必须返回相同冻结对象。

`change_hexagram`按以下步骤输出`calculation_trace`：

1. 校验并记录初爻至上爻的六个二进制值。
2. 校验、去重并排序1至6动爻位置。
3. 只翻转指定位置。
4. 通过文王序矩阵查找本卦和变卦。

旧API字典由`app/common/serialization.py`适配，不在体系模块中重复实现查表。

## 5. 测试与验收

第一阶段pytest覆盖：

- 8个八卦编号、名称、二进制双向映射。
- 64卦文王序与六爻全量双向转换。
- dataclass不可变性和非法类型、长度、爻值、动爻位置。
- 初爻、上爻和多动爻变化。
- 固定事实：萃卦`(坤下兑上)`上六动，变为否卦。
- 领域package存在且各体系实现不导入其他体系实现。

附件最终验收中的体用、世应、四课、三传和课体属于第四至第六阶段，不得伪装成第一阶段完成项。

## 6. 运行时

`backend/pyproject.toml`声明Python 3.11+和pytest。当前代码暂时保持Python 3.7语法兼容，仅用于现有服务平滑迁移；正式开发、CI和新部署必须切换到Python 3.11+。运行时升级完成后再删除旧环境兼容说明。
