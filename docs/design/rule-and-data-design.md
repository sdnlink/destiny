# 规则与数据设计

> 状态：评审稿  
> 目标：建立可追溯、可复现、可审核、可并存的术数规则和数据治理体系

## 1. 设计目标

本项目的数据难点不是数据量，而是同名概念在不同流派中含义不同、古籍版本不一、现代解释带有作者观点。设计必须防止以下问题：

- 将不同流派规则合并成一个无来源的“标准规则”。
- 修改规则后历史结果随之变化。
- 只有最终结论，没有中间计算和证据。
- 古籍原文、现代注释和AI生成文本混在一起。
- 使用来源不明或无授权的数据对外提供服务。
- 把专家案例当成真实准确率统计。

## 2. 数据域

| 数据域 | 主要内容 | 主负责人 |
| --- | --- | --- |
| 基础字典 | 五行、干支、八卦、六十四卦、九宫、方位 | 术数总顾问 |
| 历法天文 | 公农历、节气、时区、真太阳时 | 技术负责人、历法专家 |
| 流派规则 | 起卦、体用、旺衰、发传、八宅、玄空 | 分领域专家 |
| 知识文献 | 原文、版本、章节、注释、术语 | 内容负责人 |
| 标准案例 | 输入、中间值、预期输出、争议意见 | 专家、测试负责人 |
| 计算记录 | 输入快照、步骤、证据、判断、错误 | 研发负责人 |
| 空间数据 | 坐向、户型、道路、水体、高程 | 风水专家、GIS负责人 |
| 用户数据 | 人物、事项、地址、报告 | 产品、安全负责人 |

## 3. 核心实体

### 3.1 数据来源 Source

```json
{
  "sourceId": "src_...",
  "type": "classical_text",
  "title": "周易",
  "edition": "具体版本说明",
  "author": "",
  "publisher": "",
  "publishedYear": null,
  "url": "",
  "license": "public-domain",
  "licenseEvidence": "",
  "retrievedAt": "2026-08-15T00:00:00Z",
  "checksum": "sha256:...",
  "status": "approved",
  "notes": ""
}
```

`licenseEvidence`保存版权页、授权书、网页许可说明或审核记录的位置。只有`approved`来源可用于生产发布。

### 3.2 文献段落 KnowledgePassage

文献按作品、版本、卷、篇、章和段落保存。原文不直接覆盖，校勘结果作为新版本或注记存在。

必要字段：

- 段落编号和稳定引用标识。
- 来源编号、版本和位置。
- 原文、标点文本和规范化文本。
- 内容类型：经文、传、古注、现代注释、术语说明。
- 许可状态和公开范围。
- 整理人、复核人和时间。
- 上一个版本及变更说明。

### 3.3 规则 Rule与RuleVersion

Rule表示长期稳定的规则身份，RuleVersion表示某次可执行或可解释的具体版本。

规则编号建议：

```text
{体系}-{类别}-{序号}
```

示例：

- `CAL-DAYBOUNDARY-001`
- `YI-CHANGINGLINE-003`
- `MH-BODYUSE-002`
- `LIUREN-TRANSMISSION-014`
- `FS-MOUNTAIN-001`

规则版本字段：

| 字段 | 说明 |
| --- | --- |
| ruleId | 稳定规则编号 |
| version | 语义化版本号 |
| system | 历法、周易、梅花、六壬、风水等 |
| school | 流派或规则集合 |
| status | 草稿、评审、已发布、已废止 |
| title | 清晰、唯一的规则名称 |
| purpose | 规则解决的问题 |
| preconditions | 适用条件 |
| inputSchema | 输入结构 |
| procedure | 明确步骤或实现引用 |
| outputSchema | 输出结构 |
| priority | 同流派规则的顺序，不用于跨流派覆盖 |
| sourceRefs | 原文和注释引用 |
| limitations | 例外和不适用情况 |
| owner | 规则负责人 |
| reviewers | 复核人 |
| checksum | 发布内容校验值 |

### 3.4 标准案例 ValidationCase

```json
{
  "caseId": "case_mh_0001",
  "system": "meihua",
  "school": "school-a",
  "title": "时间起卦基础案例",
  "sourceRefs": [],
  "input": {},
  "expectedFacts": {},
  "expectedSteps": [],
  "expectedJudgements": [],
  "tolerances": {},
  "tags": ["basic"],
  "reviewStatus": "approved",
  "reviewers": []
}
```

案例将“事实计算”和“解释判断”分开。事实计算必须严格一致；解释判断可以保存多个专家观点，但每个观点必须注明流派和依据。

### 3.5 计算记录 CalculationResult

计算记录包含事实、步骤、证据和判断：

- Facts：起卦、盘面、干支、五行等客观派生数据。
- Steps：有顺序的计算步骤，每步关联规则编号。
- Evidence：将事实与判断连接的结构化依据。
- Judgements：特定维度、时间范围和适用条件下的规则判断。
- Warnings：输入不足、边界值、规则冲突或来源限制。

## 4. 规则生命周期

```text
draft
  → in_review
  → approved
  → published
  → deprecated
  → retired

in_review → changes_requested → draft
approved → draft（发布前发现问题）
published → suspended（紧急停用）
```

### 4.1 草稿

规则负责人录入规则、适用条件、来源和案例。草稿不能用于正式计算，只能在隔离环境运行。

### 4.2 评审

至少一名同领域专家和一名研发/测试人员参与：

- 专家确认内容、流派和来源。
- 研发确认输入输出可实现且无隐式条件。
- 测试确认正例、边界例和反例充分。

高影响规则，如换日、节气边界、三传和飞星规则，要求两名领域专家审核。

### 4.3 批准与发布

批准表示内容通过评审，发布表示可被生产任务选择。发布前自动执行：

1. 结构校验。
2. 来源和许可校验。
3. 标准案例测试。
4. 历史案例差异测试。
5. 依赖规则兼容性检查。
6. 生成不可变校验值。

### 4.4 废止

废止规则不能用于新任务，但历史任务仍可读取。若存在严重错误，应标记影响范围并提供重新计算入口，不修改原始历史结果。

## 5. 版本策略

规则使用语义化版本：

- 主版本：规则含义、算法或输出结构发生不兼容变化。
- 次版本：增加兼容分支、适用场景或新证据。
- 修订版本：文案、来源补充或不影响结果的修正。

以下变化必须产生新主版本：

- 改变换年、换月、换日边界。
- 改变起卦取数公式。
- 改变体用或用神判定逻辑。
- 改变规则优先级导致结果不同。
- 改变十五度方位区间的边界归属。

修正文献错字但不改变规则含义时，可以只增加知识内容版本，不增加规则主版本。

## 6. 规则集合与流派

一次计算不应从多个流派随机选择单条规则，而应选择经过验证的规则集合：

```json
{
  "ruleSetId": "mh-school-a",
  "version": "1.0.0",
  "system": "meihua",
  "school": "school-a",
  "rules": [
    {"ruleId": "MH-NUMBER-001", "version": "1.0.0"},
    {"ruleId": "MH-BODYUSE-002", "version": "1.1.0"}
  ],
  "defaults": {},
  "checksum": "sha256:..."
}
```

规则集合发布时锁定全部依赖版本。计算任务保存规则集合编号、版本和校验值。

## 7. 规则执行模型

MVP将规则分为三类：

### 7.1 算法规则

例如日期转换、上卦计算和变卦生成。使用经过测试的程序实现，规则记录指向实现编号和测试集。

### 7.2 映射规则

例如八卦五行、方位和类象。使用受版本控制的结构化数据表实现。

### 7.3 解释规则

例如特定体用关系在某事项下的判断。使用受限条件表达式和结构化输出，不允许上传任意可执行代码。

解释规则示意：

```json
{
  "when": {
    "all": [
      {"fact": "use_generates_body", "equals": true},
      {"fact": "question_category", "in": ["career", "finance"]}
    ]
  },
  "emit": {
    "dimension": "support",
    "polarity": "favorable",
    "strength": 0.6,
    "evidenceTemplate": "用生体"
  }
}
```

表达式语言需要白名单操作符、深度限制、超时和Schema校验。

## 8. 规则依赖

规则依赖必须显式声明。例如梅花体用判断依赖：

```text
历法时间标准化
  → 起卦取数
  → 上下卦
  → 动爻
  → 本卦/互卦/变卦
  → 体用
  → 五行生克
  → 事项判断
```

发布系统检查循环依赖、缺失依赖和不兼容版本。上游主版本变化时，下游规则自动进入“需复核”状态。

## 9. 来源与引用设计

### 9.1 引用层级

- 一级：可定位到版本、卷篇和段落的原文。
- 二级：经过授权的现代注释、学术研究或专家说明。
- 三级：项目内部整理和术语归纳。
- 生成内容：AI或模板生成，只能作为表达层，不能作为规则来源。

正式规则至少需要一个一级或二级来源；纯项目内部约定必须明确标记，不得伪装成古籍原文。

### 9.2 引用快照

规则发布时保存引用段落的内容校验值。来源后续校勘不会静默改变已发布规则的依据，新内容通过新版本关联。

### 9.3 网站缓存边界

`robots.txt` 表达自动访问偏好，不是内容版权许可。对于道人家等在线经典网站，在没有明确再利用许可或书面授权时，只缓存书目、URL、分类、校对状态、访问时间和校验值等元数据；全文、图片、下载文件和现代校订成果保持站外引用。站点自身引用第三方来源时，还需要继续核查上游权利。

## 10. 数据采集与入库流程

```text
登记来源
  → 许可审核
  → 原始文件隔离保存
  → 校验值和元数据提取
  → 文本/OCR/结构化转换
  → 人工校对
  → 章节和段落切分
  → 专家标注
  → 质量检查
  → 发布到生产知识库
```

原始层、处理中间层和生产发布层使用不同路径或数据库。未经审核内容不能通过普通搜索接口返回。

## 11. 文献处理要求

- OCR文本必须保留原图页码和置信信息。
- 繁简转换产生新字段，不覆盖原文。
- 标点整理和错字校订记录编辑者及差异。
- 同一作品不同版本并存，不以标题相同自动去重。
- 段落稳定标识不依赖数据库自增编号。
- 现代注释按授权范围控制全文、摘要或内部可见。

## 12. 数据质量规则

### 12.1 基础常量

- 枚举数量符合约束，如十天干、十二地支、八卦、六十四卦、二十四山。
- 唯一编号无重复和缺失。
- 互逆关系一致，如生克关系、坐向相差180度。
- 角度归一到`[0, 360)`。
- Unicode卦符与卦序一致。

### 12.2 历法数据

- 时间必须有时区。
- UTC与本地时间转换可逆。
- 节气时刻使用统一精度和算法版本。
- 每日干支连续递进。
- 闰月和历史夏令时有专项校验。

### 12.3 规则数据

- 有负责人、来源、适用条件和版本。
- 至少一个正例和一个边界或反例。
- 所有引用可访问且许可状态有效。
- 发布内容通过Schema和测试。

### 12.4 用户数据

- 只收集当前功能需要的信息。
- 地址和户型采用高敏感等级。
- 数据进入分析库前脱敏。
- 保留期限和删除状态可查询。

## 13. 标准案例设计

### 13.1 案例类型

| 类型 | 目的 |
| --- | --- |
| 基础案例 | 验证常规计算路径 |
| 边界案例 | 节气、子时、闰月、方位分界等 |
| 反例 | 验证规则不应触发的情况 |
| 冲突案例 | 验证不同流派并存和展示 |
| 回归案例 | 来自历史缺陷，防止再次发生 |
| 性能案例 | 验证复杂输入和批量执行 |

### 13.2 案例审批

案例录入人不能独立批准自己的案例。事实型案例由领域专家与测试人员共同批准；解释型案例可记录多个专家意见，不要求伪造一致。

### 13.3 差异比较

规则版本比较按以下层次进行：

1. 输入标准化结果。
2. 盘面事实。
3. 中间步骤。
4. 证据集合。
5. 结构化判断。
6. 最终表达文本。

表达文本变化不等同于规则结果变化，测试报告需要分别统计。

## 14. 多模型语义设计

### 14.1 统一维度

首期维度必须是受控词表，例如：

- 时机与阶段。
- 外部支持。
- 内部条件。
- 阻力与风险。
- 变化趋势。
- 行动倾向。

事业、关系、财务等是事项类别；支持、阻力、趋势等是分析维度。两者不得混为一个字段。

### 14.2 倾向枚举

建议使用：

```text
favorable / neutral / cautious / unfavorable / indeterminate
```

`indeterminate`表示规则无法判断或证据冲突，不等于中性。

### 14.3 时间范围

时间范围保存起止日期、相对阶段或无法确定。不同时间范围的判断不能直接视为冲突。

### 14.4 证据强度

强度只在同一规则体系内部使用，表示影响程度或规则优先级。跨体系比较前必须由经过评审的映射规则转换，不得解释为现实概率。

## 15. 冲突处理

冲突分为：

- 数据冲突：同一输入被不同模块标准化为不同值。
- 规则冲突：同一流派内规则给出相反判断。
- 流派冲突：不同流派采用不同前提或结论。
- 模型冲突：不同术数体系在相同维度和时间范围判断不同。
- 专家冲突：专家对解释或适用范围意见不同。

处理原则：

1. 数据冲突阻止正式计算，先修复输入或内核。
2. 同流派规则冲突由优先级或专家评审解决。
3. 流派和模型冲突保留并展示。
4. 专家冲突保存不同意见和审核状态。
5. 不使用AI自动裁决规则冲突。

## 16. 隐私与生命周期

### 16.1 数据最小化

排盘只需要时间和地点时，不要求真实姓名。问题全文不是算法必需输入时，允许用户只选择事项类别并填写本地备注。

### 16.2 分离存储

- 个人身份与计算任务使用内部标识关联。
- ClickHouse计算明细不包含明文身份。
- 报告分享使用单独脱敏快照。
- 用于产品分析的事件不含排盘内容。

### 16.3 删除

删除流程覆盖PostgreSQL、ClickHouse、对象存储、缓存、搜索索引和备份策略。法律或安全必须保留的数据只保留最小字段，并记录保留理由和到期时间。

## 17. 数据库迁移与兼容

- 所有Schema变化通过版本化迁移执行。
- 先增加兼容字段，再迁移数据，最后移除旧字段。
- 大表变更先在脱敏副本验证耗时和资源。
- JSON结果包含独立`schemaVersion`。
- 读取端至少兼容当前和上一个结果Schema主版本。
- 规则版本升级不通过数据库更新语句批量覆盖历史记录。

## 18. ClickHouse使用边界

ClickHouse适合批量计算明细、案例回归、版本差异和统计，不适合承担用户档案的事务更新。

建议表类型：

- 维度表：基础常量、发布规则索引、来源索引。
- 事实表：模块运行、步骤、证据、判断、案例测试。
- 聚合表：模块耗时、规则使用量、失败率和版本差异。

分区优先按月份或运行批次，排序键围绕任务、模块、规则版本和时间设计。敏感数据设置TTL和删除流程，不依赖TTL作为唯一合规删除机制。

## 19. 数据验收清单

- [ ] 数据源登记完整，许可证据可访问。
- [ ] 基础常量由两人复核并通过约束测试。
- [ ] 历法算法和边界规则已签署。
- [ ] 每个发布规则有唯一编号、版本和负责人。
- [ ] 规则的前置条件、步骤和输出无隐式约定。
- [ ] 标准案例达到最低数量并覆盖边界。
- [ ] 规则发布执行全量回归和差异报告。
- [ ] 文献原文、现代注释和生成文本已分层。
- [ ] 用户敏感数据没有进入日志和普通分析事件。
- [ ] 删除流程覆盖全部存储副本。
- [ ] 历史结果可以按输入和版本复现。

## 20. 待专家与数据决策

- 首期采用的经典版本及现代注释来源。
- 周易动爻和多爻变的具体规则集合。
- 梅花时间起卦的历法、取数和体用规则。
- 历法边界和真太阳时默认策略。
- 标准案例的权威等级和专家签署方式。
- 不同专家意见是否对终端用户公开。
- 规则表达式允许的操作符和复杂度。
- 古籍OCR、繁简转换和标点文本的公开范围。
- ClickHouse计算明细和审计数据的保留期限。
- 八宅、玄空和六壬的首期流派口径（八宅大游年通行传本、玄空下卦挨星已落地为 `draft`，替卦盘与多流派对照仍待确认）。
