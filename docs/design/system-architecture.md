# 系统架构设计

> 状态：评审稿  
> 目标：定义MVP的系统边界、服务职责、关键接口、数据流和运行保障

## 1. 架构目标

系统首先保证计算正确、结果可复现和敏感数据可治理，其次考虑吞吐量。MVP采用模块化单体加独立计算任务的方式，避免在规则和团队规模尚未稳定时过早拆分微服务。

架构约束：

- 事务数据和分析数据分开存储。
- 计算内核不直接访问用户数据库。
- 所有正式计算绑定不可变输入快照和规则版本。
- 单个术数模块失败不应破坏其他模块结果。
- 报告只消费已保存的结构化结果，不重新排盘。
- AI服务不在核心计算调用链中。

## 2. 系统上下文

```text
用户 / 专业顾问 / 术数专家 / 平台管理员
                    │
                    ▼
              天机演象应用
       ┌────────────┼────────────┐
       ▼            ▼            ▼
  地理编码服务   对象存储     通知服务
       │                         │
       ▼                         ▼
  时区/磁偏角数据            邮件/短信

可选外部服务：受约束AI解释、支付、合规地图和天文数据。
```

外部服务不可用时，核心排盘应继续工作。地理编码失败可以由用户手工输入经纬度；AI失败只影响解释文本，不影响结构化结果。

## 3. 总体组件

```text
浏览器
  │ HTTPS
  ▼
Web应用 / API入口
  ├── 身份与权限模块
  ├── 档案与案例模块
  ├── 规则与知识模块
  ├── 推演编排模块
  ├── 报告与分享模块
  └── 管理与审计模块
          │
          ├── PostgreSQL
          ├── Redis / 任务队列
          ├── 对象存储
          └── ClickHouse

计算工作进程
  ├── 历法内核
  ├── 周易内核
  ├── 梅花内核
  ├── 六爻内核
  ├── 大六壬内核
  └── 风水方位内核
```

MVP可以部署为一个API进程和一个计算工作进程，共享同一代码仓库。模块之间必须通过内部接口隔离，便于后续按负载或团队边界拆分。

风水方位内核只负责真北坐向、二十四山和测量误差等空间事实，不依赖历法或其他术数内核。八宅、玄空和形势规则作为后续独立规则层接入，不得反向修改原始测量事实。

## 4. 模块职责

### 4.1 身份与权限模块

负责用户、机构、成员、角色、会话和授权。它不保存排盘规则，也不执行计算。

关键能力：

- 登录、退出、令牌刷新和会话撤销。
- 基于角色和资源归属的授权。
- 管理后台多因素认证。
- 敏感操作二次确认。
- 数据导出和删除请求身份校验。

### 4.2 档案与案例模块

负责人物、事项、房屋、标签、案例和任务版本关系。原始敏感字段在此模块加密存储。

关键约束：

- 档案可修改，已提交的计算输入快照不可修改。
- 删除档案时明确处理关联任务和报告。
- 跨租户查询必须在数据访问层统一阻止。

### 4.3 规则与知识模块

负责来源、文献、术语、规则版本、审核记录和标准案例。仅发布状态的规则允许用于正式计算。

规则内容可以结构化存储，但执行代码仍需经过代码审查和自动测试。MVP不建设允许任意脚本在线执行的通用规则平台。

### 4.4 推演编排模块

负责：

- 校验模块组合和规则版本。
- 创建输入快照及幂等任务。
- 将任务分解为历法预处理和独立模块计算。
- 汇总模块状态。
- 触发对照分析。
- 保存最终任务状态和错误摘要。

编排模块不实现具体术数算法。

### 4.5 计算内核

每个内核公开相同形式的内部接口：

```text
validate(input, rule_version) -> validation_result
calculate(input_snapshot, rule_snapshot) -> calculation_result
explain(calculation_result, approved_knowledge) -> structured_explanation
```

`calculate`应为确定性函数。输入中必须显式提供时区、时间边界和流派版本，禁止从服务器本地环境读取隐式默认值。

### 4.6 报告与分享模块

负责根据固定结果快照生成网页和PDF，管理分享令牌、有效期、脱敏设置和撤销状态。

报告服务不直接查询最新规则，不重新计算。报告模板更新只改变展示，不改变保存的盘和结论。

### 4.7 管理与审计模块

负责规则发布、内容审核、数据访问审计、任务排障和系统配置。审计日志采用追加写，不允许普通管理员编辑。

## 5. 数据存储设计

### 5.1 PostgreSQL

作为业务事实的主存储：

- 用户、机构、角色和会话。
- 人物、事项、房屋和案例。
- 推演任务元数据及当前状态。
- 规则、版本、审核和发布状态。
- 报告、分享和删除请求。
- 需要事务一致性的审计索引。

建议使用UUID或有序UUID作为外部标识，不暴露连续自增主键。

### 5.2 ClickHouse

用于不可变或追加型分析数据：

- 计算输入的脱敏快照。
- 模块中间步骤和证据明细。
- 标准案例批量执行结果。
- 新旧规则差异结果。
- 性能指标和安全审计分析副本。

ClickHouse不保存明文姓名、详细地址、问题全文和户型原图。业务数据删除后，分析数据按不可逆用户标识和保留策略清理。

### 5.3 Redis与任务队列

- 会话和短期授权状态。
- API限流。
- 幂等键短期缓存。
- 计算和报告任务队列。
- 短期进度状态。

Redis不是任务结果的唯一存储。工作进程完成后必须先写入持久化数据库，再确认队列消息。

### 5.4 对象存储

- 报告文件。
- 户型图和现场照片。
- 经授权的文献原始文件。
- 导出压缩包。

文件使用随机对象键，不在路径中放姓名和地址。私有文件通过短时签名地址访问，服务端保存校验值、内容类型、大小、所有者和保留期限。

## 6. 核心数据关系

```text
User ──< ArchivePerson
User ──< Case ──< CalculationTask
Case ──< Report

CalculationTask ──1 InputSnapshot
CalculationTask ──< ModuleRun ──1 CalculationResult
CalculationTask ──0..1 SynthesisResult

Rule ──< RuleVersion ──< RuleReview
RuleVersion ──< ValidationRun >── ValidationCase
ModuleRun >── RuleVersion

Source ──< KnowledgePassage
Source ──< RuleVersion
```

任务保存的是规则版本引用和必要的规则快照校验值。即使规则被下线，历史结果仍能还原。

## 7. 任务状态机

```text
draft
  → queued
  → preprocessing
  → calculating
  → synthesizing
  → completed

queued/calculating
  → partially_completed
  → completed（重试成功）

任意运行状态
  → failed
  → cancelled
```

状态要求：

- `draft`只存在于用户确认前，不进入计算队列。
- `queued`后输入快照不可变。
- `partially_completed`必须至少有一个成功模块。
- `completed`要求所有必选模块和对照分析成功。
- 取消是尽力而为；已经完成的中间结果可按策略保留用于排障。

## 8. 计算时序

```text
用户       API       PostgreSQL     队列       Worker      ClickHouse
 │ 提交      │             │          │            │             │
 ├──────────>│ 校验/幂等    │          │            │             │
 │           ├────────────>│ 保存任务  │            │             │
 │           ├────────────────────────>│ 入队       │             │
 │<──────────┤ 返回任务编号 │          │            │             │
 │           │             │          ├───────────>│ 获取任务    │
 │           │             │<─────────┤ 状态更新    │             │
 │           │             │          │            ├────────────>│ 明细
 │           │             │<──────────────────────┤ 保存结果    │
 │ 查询      │             │          │            │             │
 ├──────────>├────────────>│          │            │             │
 │<──────────┤ 状态和结果   │          │            │             │
```

持久化顺序是先写模块结果和状态，再确认队列消息，保证进程崩溃时任务可以安全重试。

## 9. 幂等与重试

### 9.1 API幂等

创建推演和生成报告接受 `Idempotency-Key`。唯一约束至少包含用户、操作类型和键。相同键、相同请求返回原结果；相同键、不同请求返回冲突错误。

### 9.2 计算幂等

模块运行唯一键：

```text
task_id + module + rule_version + input_hash
```

工作进程重试前先查询是否已有成功结果。失败重试不覆盖旧错误记录，而是增加运行序号。

### 9.3 重试策略

- 确定性输入错误不重试。
- 临时数据库、队列或外部服务错误指数退避重试。
- 核心计算出现未捕获异常最多自动重试一次，随后进入人工排障。
- AI和报告失败不触发核心排盘重算。

## 10. API设计原则

### 10.1 资源示例

```text
POST   /v1/cases
GET    /v1/cases/{caseId}
POST   /v1/cases/{caseId}/calculations
GET    /v1/calculations/{taskId}
GET    /v1/calculations/{taskId}/modules/{module}
POST   /v1/calculations/{taskId}/retry
POST   /v1/calculations/{taskId}/reports
POST   /v1/reports/{reportId}/shares
DELETE /v1/report-shares/{shareId}

GET    /v1/admin/rules
POST   /v1/admin/rules/{ruleId}/versions
POST   /v1/admin/rule-versions/{versionId}/validate
POST   /v1/admin/rule-versions/{versionId}/publish
```

### 10.2 响应信封

成功响应返回资源本身和请求追踪编号。错误响应统一为：

```json
{
  "error": {
    "code": "CALCULATION_INPUT_INVALID",
    "message": "输入时间缺少时区",
    "fields": [{"path": "time.timezone", "code": "required"}],
    "requestId": "req_..."
  }
}
```

错误码稳定，用户文案可本地化。服务端日志通过 `requestId` 关联，不向客户端返回堆栈。

### 10.3 版本策略

API主版本放在路径中。新增可选字段不升级主版本；删除字段、改变语义或改变默认规则需要新主版本或显式兼容期。规则版本与API版本相互独立。

## 11. 内核结果契约

```json
{
  "schemaVersion": "1.0",
  "module": "meihua",
  "engineVersion": "0.1.0",
  "ruleVersion": "mh-school-a-1.0.0",
  "inputHash": "sha256:...",
  "facts": {},
  "steps": [
    {
      "sequence": 1,
      "operation": "derive_upper_trigram",
      "inputs": {},
      "output": {},
      "ruleIds": ["MH-TRIGRAM-001"]
    }
  ],
  "evidence": [],
  "judgements": [],
  "warnings": [],

```

`calculatedAt`不是计算输入，不能影响结果。JSON字段和枚举需要独立JSON Schema，并用于生产写入校验。

## 12. 安全架构

### 12.1 数据分类

| 等级 | 示例 | 控制 |
| --- | --- | --- |
| 公开 | 公版经典、公开术语 | 完整性和来源校验 |
| 内部 | 未发布规则、测试案例 | 员工/专家权限 |
| 敏感 | 出生时间、问题上下文 | 加密、最小访问、审计 |
| 高敏感 | 详细地址、户型、家庭关系 | 字段加密、严格隔离、短保留期 |

### 12.2 主要威胁与控制

- 越权读取案例：所有资源查询包含所有者或租户约束，并做自动化越权测试。
- 分享链接泄露：高熵随机令牌、仅保存哈希、默认过期、可撤销。
- 日志泄露：集中日志脱敏，不记录请求正文和敏感查询参数。
- 文件恶意上传：类型验证、病毒扫描、解码重写、私有存储。
- 规则供应链污染：规则发布双人审核、来源校验和案例回归。
- 提示注入：知识文本仅作为引用内容，AI没有规则发布和数据写入权限。

## 13. 部署拓扑

### 13.1 开发环境

Docker Compose运行PostgreSQL、ClickHouse、Redis和对象存储模拟服务。应用与工作进程可本机运行。开发数据不得使用真实用户敏感信息。

### 13.2 测试环境

与生产主要组件一致，使用脱敏案例。每次发布执行数据库迁移、标准案例、API集成、安全冒烟和报告快照测试。

### 13.3 生产环境

初期可采用容器服务或Kubernetes，但必须具备：

- API至少两个实例。
- Worker独立扩缩容。
- PostgreSQL高可用与时间点恢复。
- ClickHouse定期备份和生命周期策略。
- 对象存储版本与删除策略。
- 密钥由专用密钥系统管理。

## 14. 可观测性

### 14.1 指标

- API请求量、错误率和P50/P95/P99延迟。
- 队列长度、任务等待时间和重试次数。
- 各计算模块耗时和失败率。
- 规则版本使用量和案例回归失败数。
- 报告生成耗时和失败率。
- 数据删除任务积压和完成时间。
- 外部地理、通知和AI服务可用率。

### 14.2 日志

使用结构化日志，包含时间、级别、服务、环境、请求编号、任务编号、模块和错误码。用户编号使用内部不可逆标识，不记录输入正文。

### 14.3 追踪

一次推演从API、队列、Worker到数据库使用统一追踪上下文。长任务的每个模块创建独立跨度，便于定位性能和失败原因。

### 14.4 告警

- 核心计算错误率超过阈值。
- 队列持续积压。
- 标准案例在部署后出现失败。
- 数据库连接、磁盘或备份异常。
- 敏感接口出现异常访问量。
- 删除任务超过承诺期限。

## 15. 备份与恢复

- PostgreSQL每日全量加持续归档，定期执行恢复演练。
- ClickHouse按分区备份，计算明细可由源任务和规则重新生成时降低备份等级。
- 对象存储配置版本和生命周期，删除请求优先于版本保留。
- 规则、来源和案例作为关键知识资产单独导出。

上线前确定RPO和RTO。建议MVP目标：事务数据RPO不超过15分钟，RTO不超过4小时；知识规则RPO接近0。

## 16. 性能与容量假设

MVP规划假设：

- 注册用户10万以内。
- 日活用户1万以内。
- 峰值新建推演20次/秒。
- 单任务平均2个模块。
- 单模块结构化明细不超过1MB。
- 报告文件平均5MB以内。

容量评审必须根据试运行数据修正。优化优先级依次是正确索引、批量写入、缓存稳定基础数据和Worker横向扩容，不牺牲计算可追溯性。

## 17. 技术决策待确认

后端已采用Python/FastAPI，前端已采用React/Vite，仓库边界见ADR-003。以下事项仍待确认：

- PostgreSQL、ClickHouse和Redis的托管方式。
- 任务队列选择。
- 身份认证自建或外部服务。
- PDF生成方案和字体授权。
- 地理编码、时区、磁偏角和地图供应商。
- 是否在MVP接入AI解释。
- 生产部署使用容器服务还是Kubernetes。
- RPO、RTO及数据保留期限。
