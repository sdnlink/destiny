## 2. 项目定义

### 2.1 产品定位

天机演象是一套传统术数数字化研究与辅助分析工具。产品以统一历法、干支、阴阳五行、八卦九宫和空间方位为底座，支持周易、梅花易数、六壬、阳宅风水和堪舆等体系独立排盘，并在保留各体系原始结论的前提下进行多维度对照分析。

产品不把所有术数方法合并成一个不可解释的“答案”，而是输出：

1. 原始输入及其完整度。
2. 每个体系的排盘和中间计算过程。
3. 规则来源、流派和版本。
4. 各体系一致、互补和冲突的判断。
5. 适用范围、限制和参考建议。

### 2.2 产品原则

- **确定性计算**：历法、起卦、排盘和方位计算由程序执行，同一输入和规则版本必须得到相同结果。
- **规则可追溯**：每项判断必须关联规则、流派、版本及来源。
- **流派不混用**：存在分歧的规则并行保存，由用户或分析模板明确选择。
- **事实与解释分离**：原始数据、计算结果、规则判断和自然语言解释分别存储。
- **冲突不隐藏**：不同体系结论不一致时明确展示分歧，不强行平均。
- **隐私优先**：出生信息、地址、户型和家庭关系按敏感数据处理。
- **用途克制**：产品用于传统文化研究和民俗参考，不替代专业决策。

### 2.3 产品目标

首个可用版本应让用户完成一次完整的“建档—输入—排盘—查看依据—生成报告”流程，并让专家可以复核计算过程和规则来源。

长期目标是形成三个产品形态：

| 产品形态 | 用户 | 核心价值 |
| --- | --- | --- |
| 个人版 | 爱好者、学习者 | 标准排盘、术语解释、历史记录 |
| 专业版 | 顾问、研究者 | 多流派配置、案例管理、专业报告 |
| 机构版 | 培训及咨询机构 | 团队权限、知识库、品牌报告、审核流程 |

### 2.4 当前项目状态

当前仓库已有项目摘要、ClickHouse基础结构、基础常量种子、风水坐向验证脚本，以及完成导入和验证的多来源学习语料基础设施。道人家内部研究语料与Wikisource开放许可术数语料共1,541个文档、27,595个无损文本块和33,466,721字符；语料构建、许可隔离、分析、全文检索和只读API已经进入开发基线。历法、周易、梅花易数、六爻和大六壬的确定性计算原型、统一计算API、规则登记、工程案例回归、事项类象、元会运世背景、受约束的多模块比较和Web工作台已经实现；这些实现仍不代表相关规则通过专家验收。

项目已从数据盘点进入MVP确定性内核开发阶段。周易、梅花和六爻当前只输出盘面、步骤、关系事实与未审核类象候选；事项断语、旺衰、应期及解释规则必须等待专家审核。大六壬已形成工程原型，可输出月将、天地盘、四课、旬空、天将，以及贼克、克、比用覆盖路径内的三传；其他发传路径会明确返回未覆盖，不生成猜测值。元会运世当前只按待审核纪元计算宏观时间位置和五行关系，不映射个人吉凶。Web工作台已支持个体自动、传统时间和数字排盘：每次新起卦生成独立凭证，同一次计算可重放，各体系使用独立派生域；有限卦象空间仍允许自然撞卦。用户账号、案例档案、持久化任务和正式报告仍未建设，因此当前状态不是可上线的完整产品。特别是现有ClickHouse用户输入验证表不代表目标架构，正式设计要求用户事务和敏感原文优先保存在加密的业务数据库中，ClickHouse只接收脱敏分析数据。

## 3. 范围划分

### 3.1 MVP范围

MVP只建设能够形成稳定闭环的基础能力：

- 用户账号与基础权限。
- 人物档案、事项档案和推演记录。
- 公历、农历、节气、干支、时区和真太阳时。
- 天干地支、五行、生克和基础旺衰关系。
- 八卦、六十四卦及其基础关系。
- 周易起卦、动爻、本卦和变卦。
- 梅花易数时间起卦与数字起卦。
- 单模块结构化结果。
- 周易与梅花易数的对照展示。
- 规则来源和版本展示。
- 基础网页报告与PDF导出。
- 专家规则、经典原文和标准案例后台。

### 3.2 第二阶段范围

- 六壬天地盘、四课、三传和基础课体。
- 阳宅房屋档案、坐向和二十四山。
- 户型图上传、校准、中宫和九宫覆盖。
- 门、窗、床、灶、卫生间等空间要素标注。
- 八宅规则的独立流派实现。
- 专家客户管理和报告模板。
- 付费会员与订单能力。

### 3.3 第三阶段范围

- 三元九运及玄空飞星规则。
- 堪舆现场记录和GIS辅助分析。
- 道路、水体、高程、坡向及周边建筑数据。
- 多专家协作与争议规则评审。
- 机构版和开放API。
- 课程、案例库和研究工具。

### 3.4 明确不在首期范围

- 自动生成绝对吉凶、保证性预测或人生决策指令。
- 未经专家审核的全自动六壬、玄空或堪舆判断。
- 让大语言模型直接完成排盘计算。
- 未确认授权的古籍、课程、现代注释和案例批量入库。
- 未限定区域的全国级高精度GIS数据建设。
- 医疗、法律、投资等高风险决策建议。
- 社交社区、直播、短视频和内容广场。

## 4. 用户角色与权限

| 角色 | 主要权限 | 数据范围 |
| --- | --- | --- |
| 游客 | 查看公开案例和基础知识 | 公开数据 |
| 注册用户 | 建档、排盘、保存和导出个人报告 | 本人数据 |
| 专业用户 | 客户管理、专业参数、模板和批量报告 | 本账号客户数据 |
| 内容编辑 | 录入文献、术语和注释 | 内容库 |
| 术数专家 | 审核规则、案例和解释 | 指定专业领域 |
| 机构管理员 | 管理成员、角色、模板和机构数据 | 本机构数据 |
| 平台管理员 | 用户、套餐、审计和系统配置 | 按职责授权 |

权限必须同时满足角色权限和数据归属。平台管理员默认不能直接查看用户的敏感排盘输入，确需排障时应经过授权并保留审计记录。

## 5. 核心用户流程

### 5.1 事项推演流程

```text
创建事项
  → 选择推演体系和流派
  → 输入时间、地点、人物及问题
  → 系统校验时间与地点
  → 各模块独立计算
  → 展示排盘和中间步骤
  → 生成单模块判断
  → 对照共同点与冲突点
  → 用户查看或导出报告
```

### 5.2 阳宅分析流程

```text
创建房屋档案
  → 输入位置、建造/入住时间
  → 录入罗盘读数和测量误差
  → 修正磁偏角并判断坐向
  → 上传并校准户型图
  → 标注门、窗、床、灶等要素
  → 选择风水流派和规则版本
  → 生成分层分析
  → 专家复核并形成报告
```

### 5.3 专家规则发布流程

```text
编辑创建规则草稿
  → 关联原文和来源
  → 录入适用条件及反例
  → 添加标准测试案例
  → 同领域专家复核
  → 发布新规则版本
  → 自动执行历史案例回归
  → 通过后允许生产使用
```

### 6.6 六壬模块

六壬不作为MVP上线能力，当前实现仅为待审核工程原型。第二阶段完整需求包括月将、占时、天地盘、四课、三传、天将、旬空、遁干、课体和事项取类。当前三传只覆盖可唯一判定的贼克、克和比用，未覆盖路径返回状态和候选过程。每一种发传路径必须有标准案例，不能仅通过人工观察页面验收。

个体自动入口由独立凭证派生1至12报数确定占时，并保留真实时支；它不替代传统时间占时和用户数字报数。100人并发验收验证凭证互异、结果分布和可复算性，不要求有限盘面结果绝对不重复。

### 6.9 综合分析

| 编号 | 需求 | MVP验收条件 |
| --- | --- | --- |
| SYN-001 | 统一结果结构 | 每个模块输出维度、倾向、证据、时间和版本 |
| SYN-002 | 一致性聚合 | 相同维度和时间范围的同向判断可聚合 |
| SYN-003 | 冲突检测 | 相反判断单独列出，不被平均值隐藏 |
| SYN-004 | 模型适用度 | 权重由事项模板配置且对用户可解释 |
| SYN-005 | 数据完整度 | 缺少时间、地点或测量数据时降低等级 |
| SYN-006 | 人工复核 | 专家修改不覆盖原计算结果，并保留审计记录 |

### 6.9 报告与后台

- 报告包含摘要、输入、排盘、依据、冲突、限制和免责声明。
- 报告模板不得改变底层计算结果。
- 分享链接支持有效期、密码和撤销。
- 内容后台支持草稿、复核、发布和下线。
- 规则发布必须经过测试案例回归。
- 所有专家修订、规则发布和敏感数据访问进入审计日志。

## 7. 多模型综合设计

### 7.1 统一输出协议

每个模型至少输出以下字段：

```json
{
  "system": "meihua",
  "school": "default-reviewed-school",
  "ruleVersion": "1.0.0",
  "dimension": "事业",
  "timeRange": {"start": "2026-08-01", "end": "2026-11-01"},
  "polarity": "cautious",
  "strength": 0.6,
  "evidence": [],
  "limitations": [],
  "reviewStatus": "machine_calculated"
}
```

`strength`表示该规则在当前模型内部的影响程度，不表示事件发生概率。产品界面不得将其展示为“准确率”或“成功概率”。

### 7.2 综合步骤

1. 检查输入完整度和时间范围。
2. 按用户选择的流派独立运行各模块。
3. 将结果映射到统一分析维度。
4. 合并相同规则链产生的重复证据。
5. 标记同向、互补和冲突结论。
6. 按事项类型应用可解释的适用度配置。
7. 生成结构化综合结果。
8. 由模板或受约束语言模型生成可读文本。
9. 保存所有输入、版本、中间结果和生成记录。

## 8. 数据建设计划

### 8.1 数据分层

| 层次 | 内容 | 准入要求 |
| --- | --- | --- |
| 基础常量 | 五行、干支、八卦、节气、六十四卦 | 双人复核和自动测试 |
| 算法数据 | 历法参数、排盘规则、方位区间 | 来源明确、版本固定 |
| 流派规则 | 体用、发传、八宅、玄空等 | 专家审核、适用条件、反例 |
| 经典文献 | 原文、篇章、版本和注释 | 公版或取得授权 |
| 标准案例 | 输入、中间过程和预期结果 | 专家签字或可靠出处 |
| 空间数据 | 行政区、道路、水系和高程 | 地域明确、许可合规 |
| 用户数据 | 人物、事项、住宅和报告 | 授权、加密、可删除 |

### 8.2 数据来源要求

每个数据源必须登记名称、网址或馆藏信息、版本、许可、下载日期、校验值、处理脚本和负责人。来源不明的数据可以进入隔离区研究，但不得进入生产知识库。

工作区内现有电子书在授权状态确认前不解析、不训练、不对外提供全文搜索。

### 8.3 规则数据要求

每条规则必须包含：

- 唯一规则编号。
- 所属体系和流派。
- 规则版本和生命周期。
- 前置条件、输入和输出。
- 计算或判断步骤。
- 原始文献及现代解释来源。
- 正例、边界例和反例。
- 审核专家及审核记录。

### 8.4 案例目标

| 模块 | 开发前最低数量 | 上线前最低数量 |
| --- | ---: | ---: |
| 历法与干支 | 200 | 500 |
| 周易 | 100 | 200 |
| 梅花易数 | 100 | 200 |
| 六壬 | 150 | 300 |
| 阳宅风水 | 50 | 100 |
| 堪舆 | 20 | 50 |

数量只是下限。案例必须覆盖节气交接、闰月、子时换日、跨时区、方位临界、规则冲突和异常输入。

## 9. 技术架构计划

### 9.1 架构分层

```text
Web / 移动Web / 专业工作台
              ↓
API网关与身份认证
              ↓
用户档案  案例服务  报告服务  内容后台
              ↓
          推演编排服务
              ↓
历法内核  周易内核  梅花内核  六壬内核  风水内核
              ↓
规则仓库  知识库  案例库  地理数据  审计记录
```

### 9.2 存储职责

- PostgreSQL：用户、权限、订单、档案及其他事务数据。
- ClickHouse：计算明细、规则执行记录、批量案例、分析和审计查询。
- 对象存储：户型图、现场照片、PDF报告和原始资料。
- Redis：会话、限流、短期任务状态和缓存。
- 搜索服务：古籍、术语、案例和规则检索；早期可使用PostgreSQL全文搜索。

ClickHouse不作为用户档案的唯一事务数据库。敏感信息应在业务数据库加密保存，进入分析库时进行脱敏或使用不可逆标识。

### 9.3 规则引擎原则

- 核心排盘使用纯函数或等价的确定性实现。
- 规则配置必须经过结构校验和版本管理。
- 中间步骤可序列化并用于回放。
- 任何规则升级不得修改历史计算记录。
- 同一案例可并行运行新旧版本进行差异比较。

### 9.4 AI使用边界

允许使用AI完成术语问答、报告措辞、内容检索和结构化结果解释。禁止AI自行计算节气、干支、卦象、三传、飞星或二十四山，禁止在没有证据的情况下补充结论。

## 10. 非功能要求

### 10.1 准确性

- 历法标准案例必须100%通过。
- 已发布排盘规则的标准案例通过率必须100%。
- 专家解释允许存在观点差异，但必须显示流派和来源。

### 10.2 性能

- 普通单模块排盘服务端P95低于1秒。
- 多模型综合计算P95低于3秒，不含大型报告生成。
- 普通报告在10秒内生成；超时任务转为异步处理。

### 10.3 可用性

- 生产核心服务月可用性目标99.9%。
- 计算失败不得产生半成品正式报告。
- 异步任务支持幂等重试和状态查询。

### 10.4 安全与隐私

- 传输使用TLS，敏感字段采用应用层或数据库加密。
- 不在日志中记录完整出生信息、地址和户型数据。
- 用户数据按租户和所有者隔离。
- 分享链接默认过期且可撤销。
- 删除账户后按政策清除业务数据、对象文件和分析副本。
- 管理后台启用多因素认证和敏感操作审计。

### 10.5 可解释性

正式结论必须能够回溯到原始输入、规则版本、中间结果和来源。仅有自然语言、无法回溯证据的内容不得作为正式分析结论。

## 11. UI与信息架构

### 11.1 主要页面

- 工作台：最近案例、待处理任务和常用入口。
- 新建推演：事项、人物、时间、地点及体系选择。
- 排盘结果：原始盘、计算步骤和模块结论。
- 综合分析：一致项、冲突项、时间维度和证据。
- 房屋分析：罗盘、户型、九宫和空间要素。
- 案例库：搜索、筛选、复制、归档和对比。
- 知识库：经典、术语、规则和引用关系。
- 报告中心：生成、预览、导出、分享和撤销。
- 专家后台：规则审核、案例回归和内容发布。

### 11.2 结果页原则

结果页首先显示输入和排盘事实，再显示规则判断，最后显示综合解释。冲突结论应并列呈现。专业术语支持点击查看定义和来源，但页面不得用大量教学文案遮挡核心工作流。

## 12. 测试与验收计划

### 12.1 测试层次

- 单元测试：历法、取数、起卦、变卦、发传和方位函数。
- 参数化测试：批量运行标准案例。
- 属性测试：角度环绕、日期连续性、坐向相反等不变量。
- 集成测试：建档、计算、保存、报告完整链路。
- 回归测试：规则升级后比较历史结果。
- 安全测试：越权、敏感日志、分享链接和数据删除。
- 用户验收：普通用户可读性及专家复核效率。

### 12.2 缺陷分级

| 等级 | 定义 | 上线要求 |
| --- | --- | --- |
| P0 | 数据泄露、系统不可用、核心计算普遍错误 | 必须为0 |
| P1 | 关键流程无法完成或重要排盘错误 | 必须为0 |
| P2 | 有替代路径的功能错误或明显展示问题 | 明确计划后可少量保留 |
| P3 | 轻微体验或文案问题 | 纳入后续迭代 |

### 12.3 MVP验收门槛

- 需求范围内功能全部有验收记录。
- 历法和已发布规则标准案例100%通过。
- 用户能够完成完整推演和报告流程。
- 任一结论可追溯规则版本与来源。
- 权限、导出、删除和审计通过安全测试。
- P0、P1缺陷为0。
- 产品、技术和术数专家共同签署上线结论。

## 13. 项目阶段与里程碑

### 阶段0：立项与规则确认，4周

交付物：

- 产品范围基线和原型。
- 统一术语表。
- 历法与换日规则说明书。
- 周易和梅花易数首期流派确认。
- 数据来源及许可清单。
- 标准案例模板和首批案例。
- 技术选型与安全方案。

退出条件：开发准入清单全部通过。

### 阶段1：基础底座，6周

交付物：

- 账号、权限和档案。
- 历法、节气、干支和基础关系服务。
- 规则、知识和案例后台骨架。
- 自动化测试框架。

退出条件：历法案例全部通过，数据来源可追溯。

### 阶段2：MVP推演闭环，8周

交付物：

- 周易与梅花易数模块。
- 统一结果协议和对照分析。
- 案例记录、结果页和基础报告。
- 专家规则审核及回归测试。

退出条件：核心流程验收通过，P0/P1缺陷清零。

### 阶段3：试运行，4周

交付物：

- 邀请制测试。
- 性能、安全和数据删除验证。
- 专家与用户反馈报告。
- 正式版范围调整建议。

退出条件：达到MVP验收门槛并签署上线结论。

### 阶段4：专业模块，12至18周

按已审核规则逐步建设六壬、阳宅风水、户型分析和专业顾问能力。每个模块独立立项、独立验收，不作为一个不可拆分的大版本同时上线。

## 14. 团队与职责

| 职责 | 建议人数 | 主要责任 |
| --- | ---: | --- |
| 项目/产品负责人 | 1 | 范围、优先级、验收和跨团队协调 |
| 术数总顾问 | 1 | 术语统一、流派边界和争议裁决 |
| 分领域专家 | 2-4 | 规则、来源、案例和结果审核 |
| 后端工程师 | 2 | 业务服务、计算内核和数据治理 |
| 前端工程师 | 1-2 | 工作台、排盘、报告和户型交互 |
| UI/UX设计师 | 1 | 信息架构、原型和可用性验证 |
| 测试工程师 | 1 | 案例自动化、回归和验收管理 |
| 内容编辑 | 1 | 文献、术语、注释和版权记录 |
| 运维/安全 | 0.5-1 | 部署、监控、备份和安全审计 |

规则负责人和研发负责人必须是不同角色。研发负责正确实现已确认规则，专家负责规则内容本身的正确性。

## 15. 项目管理机制

- 两周一个迭代，每次迭代有明确演示和验收项。
- 产品需求、规则说明和接口契约分别版本化。
- 新增流派或推演体系必须经过范围变更评审。
- 每周维护风险、决策和依赖清单。
- 规则争议在专家评审中解决，不在代码评审中临时决定。
- 任何影响历史结果的改动必须发布新规则版本。

## 16. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 流派规则不一致 | 需求反复、结果争议 | 先选首期流派，规则带版本并行保存 |
| 专家参与不足 | 代码完成但无法验收 | 专家从需求阶段持续参与并对案例签字 |
| 历法边界错误 | 所有上层排盘错误 | 独立内核、权威对照和边界案例 |
| 数据版权不清 | 无法上线或产生法律风险 | 来源登记、许可审核、隔离未授权资料 |
| 项目范围过大 | 周期和成本失控 | MVP只做周易、梅花和公共底座 |
| AI解释失真 | 误导用户 | 结构化证据约束、敏感表达检测、可回溯 |
| 地址户型泄露 | 严重隐私风险 | 加密、脱敏、隔离、审计和删除机制 |
| GIS数据过重 | 成本和性能超预期 | 先选试点区域，按需下载和分层存储 |
| 用户过度依赖 | 合规和声誉风险 | 明确用途、避免确定性措辞和高风险建议 |

## 17. 预算估算框架

预算应在范围和团队投入确认后核算，至少包含：

- 产品设计与研发人力。
- 术数专家审核费用。
- 古籍、注释、地图或高程数据授权费用。
- 云服务器、数据库、对象存储、CDN和备份。
- 短信、邮件、地图、PDF和AI调用费用。
- 安全测试、隐私合规和法律咨询。
- 内容整理、案例标注和用户测试。
- 15%至20%的风险预备金。

不得只估算编码成本。规则整理、案例校验和内容授权是本项目的主要成本组成。

## 18. 运营与衡量指标

MVP阶段优先衡量质量和闭环，不以访问量作为唯一目标：

- 新建推演完成率。
- 排盘及报告生成成功率。
- 标准案例通过率。
- 结果依据展开查看率。
- 报告保存和导出率。
- 专家复核平均耗时。
- 用户主动纠错和争议率。
- 敏感数据删除完成率。
- 规则升级导致的结果变化比例。

## 19. 待决策事项

以下问题必须在对应阶段开发前确定：

1. “天机演象”是否作为正式品牌名称。
2. 首批目标用户是个人爱好者还是专业顾问。
3. 首期周易采用哪些起卦和变爻规则。
4. 首期梅花易数采用哪个版本及时间取数方式。
5. 年柱以立春还是其他边界切换。
6. 子时换日采用早子时、晚子时还是统一规则。
7. 是否默认使用真太阳时，用户能否切换。
8. MVP在并列对照之外，是否生成自动加权的综合结论。
9. 首期报告是否允许AI参与措辞生成。
10. 专家审核人、争议裁决人及签署机制。
11. 古籍版本、版权审核流程和可公开范围。
12. 用户敏感数据保存期限和删除政策。
13. 阳宅模块首个流派和试点地域。
14. 商业模式优先选择会员、专业工具还是机构服务。
