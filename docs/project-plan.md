# 天机演象项目计划书

> 本文档为项目立项摘要。开发范围、需求编号、数据准入、阶段验收和待决策事项以 [详细项目计划](./detailed-project-plan.md) 为准。

## 一、项目概述

### 1. 项目名称

项目名称：**天机演象**。

“天机演象”集合了项目的核心信息：“天机”体现传统术数对时机与规律的探索，“演”代表多维计算和综合推演，“象”涵盖卦象、数象、时象以及堪舆中的形势与空间之象。名称能够覆盖周易、梅花易数、六壬、阳宅风水和堪舆等功能，同时保留传统文化产品应有的辨识度。

### 2. 项目定位

本项目拟建设一套融合五行八卦、周易、梅花易数、六壬、阳宅风水及堪舆学的综合分析平台。

平台通过统一历法、干支、阴阳五行、八卦九宫等基础数据，将不同术数体系转化为可计算、可追溯、可配置的推演模型。用户输入时间、地点、人物信息、房屋信息或具体事项后，系统分别调用相应模型进行计算，再通过综合分析引擎输出多维度结果、依据说明、趋势判断及参考建议。

项目的核心不是简单生成一段结论，而是建立完整、透明的推演过程：

```text
用户输入
  ↓
历法与空间数据标准化
  ↓
多个术数模型分别推演
  ↓
提取共同指标与冲突指标
  ↓
按场景、适用性和可信度进行加权
  ↓
输出综合结论、推演依据与差异说明
```

### 3. 产品边界

平台定位为传统文化研究、知识学习和民俗参考工具，不宣称结果具有科学预测能力，不替代医疗、法律、金融、心理咨询等专业服务。

涉及用户出生日期、地址、户型、家庭关系等敏感数据时，平台应遵循最小化收集、明确授权、加密存储和用户可删除原则。

## 二、项目目标

### 1. 业务目标

- 建立统一的传统术数数字化知识体系。
- 支持不同流派、规则和参数独立配置。
- 实现单模型排盘与多模型综合推演。
- 让每项结论均可查看来源、规则及计算过程。
- 支持个人用户、传统文化研究者及专业顾问使用。
- 逐步形成课程、报告、咨询和专业工具等商业模式。

### 2. 技术目标

- 建立统一历法与干支计算基础设施。
- 将术数规则与业务代码适度分离，便于修订和扩展。
- 对同一输入保证计算结果稳定、可复现。
- 为每种算法建立权威案例和自动化测试。
- 支持新增流派时复用基础数据与推演能力。
- 确保综合结果能够解释“为什么得出这一判断”。

### 3. 首期目标

第一期不追求一次覆盖所有术数体系，而是完成一条可靠的核心链路：

1. 输入出生时间、起卦时间或事项信息。
2. 完成历法转换、干支排布和五行分析。
3. 支持周易、梅花易数两类核心推演。
4. 输出结构化结论和推演依据。
5. 保存案例并生成标准报告。

## 三、目标用户与使用场景

| 用户类型 | 核心需求 | 主要功能 |
| --- | --- | --- |
| 传统文化爱好者 | 学习基础知识、体验排盘 | 基础排盘、术语解释、案例演示 |
| 进阶研究者 | 比较流派和推演过程 | 参数配置、规则追踪、结果对比 |
| 专业顾问 | 提高排盘和报告效率 | 客户档案、专业排盘、报告导出 |
| 房屋使用者 | 了解住宅空间布局 | 户型标注、方位分析、调整参考 |
| 内容与培训机构 | 建设课程和案例库 | 知识库、课程案例、权限管理 |

典型应用场景包括：

- 根据时间、人物信息和所问事项进行综合推演。
- 使用梅花易数按时间、数字或外应起卦。
- 使用六壬进行专项课式分析。
- 上传或绘制户型图，结合坐向和时间分析住宅。
- 比较不同方法对同一事项的判断。
- 查看结论对应的卦象、五行关系和规则出处。
- 生成可分享或打印的分析报告。

## 四、产品功能规划

### 1. 用户与案例管理

- 手机号、邮箱或第三方账号登录。
- 个人资料和隐私设置。
- 人物档案、事项档案、住宅档案。
- 历史推演记录和条件检索。
- 案例复制、标签、备注及归档。
- 数据导出与账号注销。

### 2. 基础历法引擎

基础历法引擎是整个项目的公共底座，主要包括：

- 公历、农历、干支历转换。
- 真太阳时和时区校正。
- 二十四节气精确时间。
- 年、月、日、时四柱计算。
- 天干地支、藏干、旬空、纳音。
- 阴阳、五行、生克制化关系。
- 八卦、六十四卦、九宫和方位映射。
- 地理经纬度、磁北与真北参数。
- 不同历法边界规则配置。

### 3. 五行综合分析

- 五行数量、强弱和分布分析。
- 天干地支及藏干贡献计算。
- 月令、季节和旺相休囚死分析。
- 生、克、泄、耗、助关系。
- 五行偏旺、偏弱和失衡提示。
- 时间、人物、事项和空间五行交叉分析。
- 图表化展示五行关系及权重来源。

系统不能只按“五行出现次数”得出结论，应区分显性元素、藏干、季节权重、组合关系及不同流派规则。

### 4. 周易模块

- 六十四卦基础资料库。
- 卦辞、爻辞、彖传、象传等内容管理。
- 本卦、互卦、变卦、错卦、综卦分析。
- 动爻、体用、上下卦及卦气关系。
- 手工起卦、数字起卦和时间起卦。
- 卦象与事项类型映射。
- 原文、注解和推演结论分层展示。

### 5. 梅花易数模块

- 年月日时起卦。
- 数字、声音及方位起卦。
- 上卦、下卦和动爻计算。
- 体卦、用卦及五行生克分析。
- 本卦、互卦、变卦综合判断。
- 旺衰、应期和事项分类规则。
- 起卦参数及全过程回放。

### 6. 六壬模块

六壬建议作为第二阶段重点能力建设：

- 月将、占时和天地盘。
- 四课、三传排布。
- 天将、神煞及旬空。
- 九宗门等发传规则。
- 课体识别和事项分类。
- 不同流派规则配置。
- 原始课盘与解释结论对照展示。

六壬规则复杂且流派差异明显，需要由领域专家整理规则优先级，并为每一种课式准备标准案例。

### 7. 阳宅风水模块

- 当前基础能力：磁偏角修正、坐向换算、二十四山判定、洛书九宫数据。
- 地址、经纬度和建筑时间录入。
- 坐向测量及误差范围设置。
- 户型图上传、缩放和校准。
- 中心点、门、窗、灶、床、卫生间等标注。
- 八宅、九宫及五行方位分析。
- 楼层、外部道路和周边环境记录。
- 家庭成员与住宅空间关系分析。
- 调整方案的依据、优先级和限制条件说明。

### 8. 堪舆分析模块

- 地形、朝向、水系和道路信息采集。
- 卫星地图或地理信息辅助标注。
- 山、水、向及空间关系记录。
- 罗盘分金和方位数据。
- 不同勘测时间的现场记录。
- 图片、视频、文字和测量数据归档。
- 专业人员人工修正和复核。

该模块依赖高质量现场数据，首期应定位为辅助记录和分析工具，不宜仅凭地图信息直接生成确定性结论。

### 9. 多模型综合推演引擎

综合引擎是项目的主要差异化能力。建议采用“指标归一化、证据汇总、冲突呈现”的方式，而不是将各模块结论简单相加。

每个推演模块统一输出如下结构：

```json
{
  "dimension": "事业趋势",
  "conclusion": "短期存在阻力，宜先调整内部条件",
  "polarity": -0.35,
  "confidence": 0.72,
  "timeRange": "未来三个月",
  "evidence": [],
  "ruleVersion": "meihua-1.2.0"
}
```

综合分析包括：

- 相同结论聚合。
- 不同结论冲突检测。
- 按问题类型设置模型适用权重。
- 按输入数据完整度计算可信等级。
- 区分事实数据、规则推导和解释性文本。
- 输出主结论、辅助结论和保留意见。
- 展示每个结论由哪些模型支持。
- 避免使用虚假的“精确概率”掩盖规则不确定性。

### 10. 报告系统

- 快速摘要版报告。
- 专业推演版报告。
- 分模块详细报告。
- 图表、卦盘、课盘和户型分析图。
- 推演依据与规则版本。
- PDF、图片及网页分享。
- 报告模板和机构品牌配置。
- 敏感信息脱敏与分享有效期。

### 11. 知识库与后台

- 经典原文和现代注释管理。
- 术语、卦象、课式和案例管理。
- 流派及规则版本管理。
- 专家审核和内容发布流程。
- 错误案例反馈。
- 用户权限、套餐和订单管理。
- 操作日志和敏感操作审计。

## 五、系统总体架构

```text
Web端 / 移动端 / 专业工作台
              ↓
         API服务层
              ↓
用户中心  案例中心  报告中心  支付中心
              ↓
       综合推演编排引擎
              ↓
历法引擎  五行引擎  周易引擎  梅花引擎
六壬引擎  阳宅引擎  堪舆辅助引擎
              ↓
规则库  经典知识库  案例库  地理数据
              ↓
关系数据库 / 缓存 / 文件存储 / 搜索服务
```

推荐技术方向：

- 前端：Vue 3 或 React，适配电脑端和移动端。
- 后端：Java Spring Boot、Go 或 Python FastAPI。
- 数据库：PostgreSQL。
- 缓存：Redis。
- 文件存储：兼容 S3 的对象存储。
- 搜索：首期使用 PostgreSQL 全文搜索，数据规模扩大后引入 Elasticsearch。
- 地图能力：根据目标市场选择合规地图服务。
- 算法实现：核心规则采用确定性程序，人工智能只负责解释、问答和报告润色。
- 部署：Docker 容器化，区分开发、测试和生产环境。

不建议让大语言模型直接完成排盘计算。较可靠的方案是由确定性算法生成结构化结果，再让语言模型在受控数据范围内负责自然语言表达，以减少计算错误和无依据扩展。

## 六、数据与规则设计

### 1. 核心数据对象

- 用户与组织。
- 人物档案。
- 事项及问题。
- 时间与历法数据。
- 地点与经纬度。
- 房屋和户型。
- 卦盘、课盘及推演任务。
- 单模型推演结果。
- 综合结论和证据。
- 报告。
- 规则、流派和版本。
- 经典文献及引用来源。

### 2. 规则版本管理

每次计算必须保存：

- 原始输入数据。
- 时区和真太阳时设置。
- 使用的流派。
- 算法及规则版本。
- 中间计算结果。
- 最终结论。
- 人工修改记录。

通过版本管理保证历史报告可复现，并能在规则升级后对比新旧结果。

### 3. 知识来源管理

知识条目应记录书名、篇章、原文、注释者、版本和适用流派。古籍原文、现代解释、系统推导与人工意见必须明确区分，避免来源混杂。

## 七、实施阶段

| 阶段 | 周期 | 主要交付 |
| --- | ---: | --- |
| 需求与知识建模 | 3-4周 | 产品原型、术语表、规则边界、标准案例 |
| 基础平台建设 | 5-6周 | 用户、档案、历法、干支、五行底座 |
| MVP核心功能 | 6-8周 | 周易、梅花易数、结果页、基础报告 |
| 综合推演能力 | 4-6周 | 指标体系、证据聚合、冲突分析 |
| 专业能力扩展 | 8-12周 | 六壬、阳宅、户型标注、专家后台 |
| 测试与试运营 | 4-6周 | 算法校验、安全检查、灰度发布 |
| 持续建设 | 长期 | 堪舆辅助、机构版、开放接口、课程体系 |

MVP预计需要4至6个月。若首期同时完整建设六壬、阳宅和堪舆模块，项目周期可能扩大至8至12个月。

## 八、团队配置

建议的基础团队包括：

- 产品负责人1名：负责产品范围、用户流程和版本规划。
- 领域专家2至4名：分别负责易学、梅花、六壬和风水规则。
- 后端工程师2名：负责基础服务、规则引擎和数据系统。
- 前端工程师1至2名：负责排盘、报告和户型交互。
- UI/UX设计师1名：负责信息密集型界面设计。
- 测试工程师1名：负责功能、算法和回归测试。
- 内容编辑1名：负责经典资料、术语和案例整理。
- 运维或安全工程师0.5至1名：前期可由后端工程师兼任。

领域专家不应只在验收阶段参与，而应持续负责规则定义、案例校验和争议处理。

## 九、质量保障方案

### 1. 算法测试

- 为历法边界、节气交接、跨时区建立专项测试。
- 每种起卦方式建立固定输入和标准输出。
- 每种六壬课式建立专家确认案例。
- 为房屋方位临界值设置误差测试。
- 对规则升级执行历史案例回归测试。

### 2. 专家验证

建议建立三级验证机制：

1. 开发人员根据规则文档实现。
2. 领域专家使用标准案例核对。
3. 不同专家对争议结果交叉复审。

### 3. 可解释性要求

每项重要结论至少包含：

- 使用了什么输入。
- 应用了什么规则。
- 得到了什么中间结果。
- 哪些因素支持该结论。
- 哪些因素与该结论冲突。
- 结论的适用范围与限制。

## 十、商业模式

可采用分层收费方式：

- 免费版：基础排盘、有限次数和简要解释。
- 个人会员：完整报告、历史案例和多模型分析。
- 专业版：客户管理、规则配置、报告模板和批量导出。
- 机构版：团队账号、品牌定制、课程及案例管理。
- 专家服务：预约咨询，平台收取技术服务费。
- API服务：向传统文化平台、内容机构提供标准计算接口。
- 数字内容：课程、古籍注解、专题案例和研究资料。

商业化过程中应清楚区分“软件计算服务”和“专家咨询服务”，避免将自动结果包装为确定性承诺。

## 十一、风险与应对

| 风险 | 表现 | 应对方案 |
| --- | --- | --- |
| 流派差异 | 同一输入产生不同结果 | 明确流派、版本和规则来源，不强行统一 |
| 算法错误 | 历法边界或排盘结果异常 | 建立标准案例库、自动测试和专家复核 |
| AI生成失真 | 解释内容偏离计算结果 | 使用结构化结果约束生成，禁止AI自行排盘 |
| 数据质量不足 | 时间、方向或户型输入不准确 | 输入校验、误差提示和可信等级 |
| 用户过度依赖 | 将结果用于重大决定 | 风险提示、限制性表述和专业服务声明 |
| 隐私泄露 | 出生信息、地址和户型被暴露 | 加密、权限隔离、脱敏和删除机制 |
| 范围失控 | 首期同时实现全部流派 | 先完成MVP，再按模块扩展 |
| 内容版权 | 现代注释或课程未经授权 | 建立来源及授权记录，优先使用合规内容 |

## 十二、验收指标

MVP建议使用以下指标验收：

- 标准历法案例计算一致率达到100%。
- 周易和梅花标准案例通过率达到98%以上。
- 所有结果均保存输入、规则版本和中间过程。
- 核心计算接口平均响应时间低于2秒。
- 报告生成成功率达到99%以上。
- 关键页面兼容主流电脑和移动设备。
- 敏感数据支持查看、导出及删除。
- 专家能够在后台定位每一项结论的规则来源。
- 系统出现模型冲突时能够明确展示，而非隐藏差异。

## 十三、近期执行计划

项目启动后的前30天建议完成以下工作：

1. 确定首期只覆盖五行、周易和梅花易数。
2. 确定历法、换日、节气和真太阳时规则。
3. 建立统一术语表和规则文档模板。
4. 收集不少于100个标准排盘案例。
5. 完成用户输入、排盘、综合结果和报告原型。
6. 设计统一的“证据-判断-结论”数据结构。
7. 完成技术选型、数据库设计和接口规范。
8. 明确隐私政策、免责声明及内容审核机制。

## 十四、项目结论

项目成败的关键不在于首期包含多少术数门类，而在于三个基础能力：**计算准确、规则可追溯、不同体系之间能够解释性地综合**。

首期应集中完成统一历法底座、五行分析、周易、梅花易数和综合报告链路。在基础规则与标准案例经过验证后，再扩展六壬、阳宅和堪舆模块，以控制项目范围和实施风险。
